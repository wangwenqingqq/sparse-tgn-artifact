**第一个根本问题是模型合同。** 记录从 TGN 转向 DyGFormer 共现，再集中到 TNCN mode 2，验收文字却持续写“完整原始 TGN”。这几个对象不能互换。原始 TGN 的训练时序、TGN 主干配 TNCN 解码器，以及单独初始化的 TNCN 解码器，应有各自的运行入口和性能分母。TNCN 论文自身也把历史读取、节点表示、CN 提取、聚合和 memory 更新列为不同阶段。[TNCN 论文及伪代码](https://arxiv.org/html/2406.07926v2)

本轮对上传记录的研究不替用户改变原目标。建议后续实现首先明确写成“固定版本 TNCN mode 2 的解码流水线”，然后单独验证它在目标完整模型中的占比和任务质量。如果最终仍要求 Rossi 原版 TGN，则目前这些 TNCN 实验只是探索性证据，不能充当其达标结果。

**第二个根本问题是一个容易被忽略的源码副作用。** 固定版本 TNCN 在取得选中行后，对 `i_1_v`、`i_2_v` 等调用 `fill_value_(1.0)`。检查 torch_sparse 0.6.18 可见，该方法经 `set_value_` 修改对象并返回自身。因此这些选中行后续参与计算时已经是支持指示量；这与“始终保留 A² 路径权重”的实现不同。[固定 TNCN 源码](https://github.com/GraphPKU/TNCN/blob/4c93a2a6c67c4033bab50a2c0a6833cbf8f24b5b/modules/NCNDecoder/NCNPred.py#L99-L149)、[torch_sparse 0.6.18](https://github.com/rusty1s/pytorch_sparse/blob/0.6.18/torch_sparse/tensor.py#L295-L310)

这解释了记录中布尔化和三角分支消除为什么可能成立，也限制了它们的科学外推范围：应描述为该实现合同下的精确优化，不能直接称为 TNCN 的普遍数学性质。另一个固定版本 TGM 的 `_fill` 返回新稀疏张量，进一步说明同名模型不保证相同别名语义。[TGM 对应实现](https://github.com/tgm-team/tgm/blob/d3cdd9f1c49c091c5ca5b6640d326444e4809f0e/tgm/nn/decoder/ncnpred.py#L48-L55)

当前精确简化可沿用记录里的定义：对称非负整数邻接 A、P=support(A)、Q=support(A²)，查询 (u,v) 的 a=P[u]、b=P[v]、h=Q[u]、k=Q[v]、e=A[u,v]、S=(a⊙b)A。在保留其条件掩码 M、端点和时间衰减规则时，C22=M⊙(h⊙k+S)。这里 h、k 是二值量，S 和 e 仍有权重；C12/C21 可以有负值。**BMMA 给出的布尔支持或交集计数，不等于全部加权 C。**

还有一个时间语义边界：在合法历史采样图上算两跳支持，不自动等于沿路径强制 t1<t2 的事件 walk 计数。文档早期的严格事件时间 oracle 与后期 TNCN 采样图计算，需要分别命名和验证。不能把前者的因果证明直接转给后者。

**第三个问题是验收层级。** 原文第 19060 行说明，648 步使用 18 个 before 图状态、固定合成初始 X、未训练 MLP、无时间衰减，以及两步仅更新模型参数的 Adam；X 不参与 Adam。141,192 是字段比较数，包含非浮点结构和相关的成对比较，不是独立训练试验数。

所以这项结果值得保留，但它没有修复另外 7 个组合梯度反例，没有证明训练后嵌入上的稳定性，也没有覆盖完整 memory 更新和长期收敛。后续无需为了同一个初始化诊断无限扩测；应把有限实验预算移到实际训练状态和新内核本身。

**第四个问题是性能空间可能比直觉小。** 设待优化部分占原完整时间 f，其局部加速为 s，暂忽略新增开销，则完整加速是：

\[
S_{total}=\frac{1}{1-f+f/s}.
\]

若完整目标为 1.10×，必须满足 f(1−1/s)≥0.090909。免费消除一个阶段也至少要消除完整时间的 9.09%；该阶段加速 2× 时，要占原时间至少 18.18%；加速 4× 时至少占 12.12%。这是代数条件，不依赖某张卡的峰值。

以记录中的解码器 1.1138× 作条件例子：假设该比值能原样保持、其他部分完全不变，解码器需占完整任务时间至少 **88.98%**，才能贡献完整 1.10×。这不是对当前 TGN 占比的估计，而是说明为什么必须先拿完整训练 profile。早期免费关系构造 1.224× 对应旧诊断分母约 18.30% 的可消除时间，也不能沿用为更强基线下的新上限。

**第五个问题是“联合”需要物理证据，但不需要神秘的逻辑独占性。** 对 shared epoch 的否定是成立的：给定两套等价的输入证书，联合方案不会独占新的可复用结果。不过，逻辑工作相同的两种实现仍可能有不同的寄存器占用、布局转换、访存和调度成本。

后续合理的问题是：在相同语义和同等优化权利下，联合布局是否降低实际完整成本。无需要求 SIMT 在逻辑上绝对不能模仿该方法。反过来，给独立方案同样的布局以后若双方执行图已相同，那么这个变体只构成布局归因控制，不能再当作另一种独立算法。

应保留普通、仅 BitTC、仅 SparseTC、双 TC 独立、双 TC 联合这些消融；另外补一个同等融合的 dense-TC 消费者。它能直接检验收益究竟来自片上融合，还是来自原生结构稀疏指令。基线若接受了候选的具体布局，应再保留一个自行构建布局的强实现，分别回答归因和实际竞争力。

**本轮的新结果是一个前向布局可行性证据。** 按 NVIDIA 的 warp MMA ABI，我检查了四个 16×8 的 B1 输出面板组成 16×32 逻辑 tile 后，转成 FP16/BF16 sparse m16n8k32 A 操作数的线程位置。ABI 来源为官方 PTX 的 B1 累加器、稀疏 A 和元数据布局。[NVIDIA PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/)

下面的映射与计数是本轮推导和 CPU 程序结果，不是 GPU 测量。设线程 lane=4g+t，其中 t∈{0,1,2,3}。每个 B1 面板中，该线程拥有行 g/g+8、面板列 2t/2t+1 的输出。SparseTC 消费者则要负责行 g/g+8、逻辑列区间 4t…4t+3 以及 16+4t…19+4t 的两个选中值。

如果四个 B1 面板按连续列 0…7、8…15、16…23、24…31 排列，512 个候选值位置中有 384 个落在别的消费者线程。对每四列恰好两个非零的情况，256 个实际值中有 128–256 个需要跨线程转交。这只针对该朴素列顺序，不能当作所有实现的下界。

可以改变 B1 面板的列节点顺序，使同一线程在两个面板中凑齐自己所需的四个候选值：

| 面板 | 8 个输出列对应的逻辑节点位置 |
|---|---|
| 0 | 0, 1, 4, 5, 8, 9, 12, 13 |
| 1 | 2, 3, 6, 7, 10, 11, 14, 15 |
| 2 | 16, 17, 20, 21, 24, 25, 28, 29 |
| 3 | 18, 19, 22, 23, 26, 27, 30, 31 |

对面板 p 和槽位 j，其逻辑列为：

\[
z=16\lfloor p/2\rfloor+4\lfloor j/2\rfloor+2(p\bmod2)+(j\bmod2).
\]

代入 j=2t 或 2t+1，可见同一线程得到的是自己的 SparseTC 四列组。于是，在**系数其余输入也能送到这些线程**的前提下，值的选取与 half2 打包可在线程内完成，不必先交换这些候选值。

这里没有改变最终逻辑列次序：置换的是 B1 的输出列任务与输入节点加载次序，SparseTC 和 X 仍按逻辑列消费。B1 输入 gather 的顺序和局部性会变化，真实成本尚待计量。查询 u/v 的 Q 行还应按查询行角色各自对齐；重复根是否重算、共享根是否缓存，都要单独收费。

| 本轮 CPU 检查 | 结果与范围 |
|---|---|
| FP16/BF16 前向候选值位置 | 512 个全部匹配消费者线程；朴素顺序只有 128 个匹配 |
| 每个四列组的全部支持模式 | 128 个四列组 × 16 种模式，共 2,048 个局部编码用例通过 |
| B1 整数点积与 K 分块尾部 | 10 个 K 长度 × 2 种列顺序，共 20 个用例一致 |
| 带符号矩阵编码、前向和转置乘法 | 64 个小整数 tile 通过；转置检查仅验证数学值，不是反向线程布局 |
| 稀疏元数据 | 所建编码中每平面 128 个 nibble 有 96 个要汇集到不同线程 |
| TF32 sparse m16n8k16 | 另外检查了 256 个候选位置；其 1:2 结构与连续 B1 列对本已对齐，仅验证位置 |

**这不是“零转换联合内核”。** 值位置对齐后，仍有元数据汇集、类型转换、寄存器活跃区间、输入位图装载，以及真实 C 的构造。上述 384 和 96 都是逻辑数据位置数量，不能读成 shuffle 指令条数、HBM 字节数或延迟。

这个结果也不能叫作已通过新颖性审查的算法。它是对“布局不一致是否一定要搬值”的一个建设性答案；采用同样列顺序的独立实现也可以使用它。它没有推翻记录里旧的双向共享格式结论，因为本轮只解决另一种布局下的前向值归属。

**建议检验的候选流水线。** 对每个固定历史采样图，按查询组和被请求节点 tile 安排 u/v 的 Q 计算；通过上述列面板顺序，将二跳支持送到加权系数消费者线程。在同一位置结合 a、b、e、S 和通道规则产生 C，生成合法稀疏操作数，立即消费当前 X。是否留存或重建反向所需状态，作为单独成本决策。

本轮没有实现完整 TNCN 内核。尤其 S 的加权生成与分发尚未解决：不能把它当作免费输入，否则只是在把旧的 handoff 问题移到另一个位置。

| 必付成本 | 验证时要回答的问题 |
|---|---|
| B1 输入准备 | P 的位打包是否已有？新的列顺序是否增加 gather、重复加载或尾部浪费？ |
| Q 的工作量 | 每个面板实际需要多少输出？是否因为按查询排根而重复计算同一 Q 行？ |
| S、e 与其他系数输入 | 带权结果从哪里生成、哪个线程持有、何时到达？ |
| 精确稀疏编码 | 一个四列组有 3/4 个非零时，用两平面或其他精确路径；其额外 MMA 不能省略 |
| 特征精度 | 小整数 C 可以精确表示，不代表连续 X、梯度能无损转成 FP16/BF16/TF32 |
| 反向 | Cᵀ 的行方向、metadata、gather、累加和保存/重算分别如何安排？ |
| 当前强基线 | 它究竟还物化了哪份 Q/S/C？只统计实际存在且被消除的中间传递 |
| 占用与调度 | 保留两套 Q、多个通道、X 与输出累加器后，是否发生 spill 或并行度下降？ |

每四列最多拆成两组只是一个精确表示方式；若每个 tile 都要发两次 sparse MMA，同范围的算术优势可能被抵消，还要支付 metadata。也不能把 SparseTC 和 BitTC 视为可独立相加峰值的两套引擎。

选择硬件时，先区分 PTX 接口、实际 SASS 和实测执行。上传记录报告 CUDA 13.1 下 Ampere 有 BMMA、RTX Blackwell 的 B1 被展开成 IMMA；本轮没有重新编译确认。官方文档也明确区分 B1 AND/XOR 的支持条件和部分变体移除，不能凭“新卡支持 Tensor Core”直接推断原生 B1 能力。[CUDA 13.1 编程指南](https://docs.nvidia.com/cuda/archive/13.1.0/cuda-c-programming-guide/index.html#sub-byte-operations)

**下一步应是一次有限的完整成本验证。** 按下面的顺序推进即可，不必先恢复被否定的缓存分支，也不必先写论文摘要。

1. 固定目标完整模型、源码、采样/负样本、batch 可见性、训练质量标准；用实际训练状态测出当前强基线的阶段占比。保留原 1.10× 目标，不把局部诊断改叫完整任务。
2. 在相同真实采样数据上，比较朴素面板与消费者列面板。统计请求输出利用率、实际 2:4 平面数、输入 gather、S 的交付、metadata 和前反向状态量。历史 before/after32 窗口可用于回归，但不能替代训练分布。
3. 以明确支持原生 B1 的目标卡做一个包含实际系数生成的小 tile 内核。计入动态输入准备；检查 SASS、数值正确性、寄存器/spill 和完整耗时。仅值传递 microbenchmark 作为归因控制，不作为主结果。
4. 比较同等融合的 SIMT、dense TC、SparseTC，以及双 TC 独立/联合。先看候选是否赢当前强实现，再解释硬件归因。联合方案不必每个拆分件都独立获胜。
5. 若关系流水线有足够收益，再覆盖反向、训练后嵌入、真实损失和完整训练质量。原失败用例继续保留；新的质量实验不能抹去旧数值反例。

明确停止条件：若当前完整 profile 的乐观收益上限已达不到目标，或付清 S、packing、反向与占用成本后候选不优于强基线，就关闭这一实现。若联合 SparseTC 路径始终输给同等融合的 dense TC，则该结果也不能支撑“原生稀疏＋位 Tensor Core 联合优势”的主标题。

本轮交付的可用成果是：证据边界审查、近邻论文约束、一个前向消费者布局的构造与 CPU 验证，以及完整成本实验的具体对象。**方向可以继续，但论文主张仍要靠真实流水线收益建立。**
